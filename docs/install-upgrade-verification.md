# KEJ-83: installation, historical upgrade and recovery

This profile covers HW-14-02..04 and the actual backup-recovery dependency from
HW-09. It is implementation evidence, not a new model checker or a claim that a
whole multi-version migration is one transaction.

## Reproduce

Use the repository's Node 24+ installation and preflight instructions, then:

```sh
npm run verify:upgrade -- --release
npm run verify:upgrade:report -- verification-evidence/upgrade/run-... --release
```

The profile has a 300-second outer budget. Data scenarios have a 60-second process
budget; the separate installer has 240 seconds, with each npm install capped at
90 seconds, build at 30, startup at 15 and shutdown at 3. The CI job has ten minutes
including dependency setup and artifact upload. The synchronous migration barrier
has a ten-second deadline; each test/scenario and process exit is also bounded.
Normal `npm test` runs the focused regressions, never nested npm installations.
The fault-test file runs exclusively to avoid multiplying subprocess contention.

`UPGRADE_NPM_CACHE=/absolute/cache` can reuse a package cache, never another
checkout's installed dependencies. The report records that choice. Without it,
the installer creates a fresh cache. Restricted environments need a writable
cache and permitted package-registry route. Missing downloads are failures, not
permission to substitute an existing node_modules tree. No paid providers, real
keys, new runtime API or production database changes are introduced.

## Real historical data and independent oracle

The frozen manifest and per-version schema/row JSON contain actual schemas v1–12, generated by importing each full
pinned original Git commit's ListeningStore plus its original relative modules.
`sourceFiles` records SHA-256 for every executed historical source. The generator
uses those original public APIs to save synthetic history, original/translated
segments, aliases/mentions, knowledge, completed and unfinished extraction jobs,
pending/failed translations, v4+ in-flight paid checkpoints, v6+ relations with
assertions/supports/request history, v10+ manual edits/facts/correction rules and
v11+ successful and interrupted edit receipts. Time and UUID are fixed only in
this isolated maintainer generator. It blocks fetch and records zero calls.

Regenerate only with the pinned historical objects already available locally:

```sh
node scripts/generate-upgrade-fixtures.mjs
```

The manifest fixes the exact ordered versions 1–12 and both filenames/digests per version; missing, repeated, swapped or changed parts are rejected. Each version retains the same source provenance and complete rows.

Runtime CI uses committed text fixtures; it neither downloads nor executes Git
history and never lowers a current database's user_version to impersonate an old
schema. Materialization installs the original tables, inserts original records,
then original indexes/triggers, and verifies primary keys, columns, integrity and
foreign keys. Turning foreign keys off is limited to snapshot reconstruction.
The actual application upgrade runs with its ordinary foreign-key settings.

The target v12 schema is frozen from integration commit
66059a1d9bcc855dfd77379b9ec079f13baa3148. `target-provenance.json` binds its digest,
production migration source hashes and first-transaction SQL statement digests.
These contracts require explicit review when migrations change. SQL comparison
preserves word boundaries, quoted identifiers/literals, constraints, indexes and
triggers; only inter-token whitespace and unquoted keyword case are ignored.

The independent oracle compares every target table, row and field by primary
key. Newly introduced columns use the frozen historical target's defaults.
Only explicit transformations are allowed: interrupted active runs get an end
time, running extraction returns to pending, old v2/v3 prompt-2 work becomes
LEGACY_RECOVERY_REQUIRED, in-flight extraction becomes pending with paid counts
retained, enabled relations wait for a key, old quota columns disappear, and
relation cache fingerprints normalize without changing the saved input's other
fields or request history. Constructor recovery and server-only edit-receipt
recovery are checked separately. Import additionally fails pending translations,
fences unfinished extraction and requires explicit retry. Whole task tables or
JSON payloads are never excluded from comparison.

All twelve upgrades query real history/knowledge, make a current public title/notes
metadata edit with an exact all-table expected projection, then reopen and compare the durable result.
The v6-only legacy relation run receives the documented paused recovery record.

## Faults and actual recovery

For each v1–11 input, SIGKILL occurs immediately before and after the first real
pending migration COMMIT. Additional v1/v6/v11 cases stop after the first DDL.
A test-only preload wraps the real SQLite exec; it never inserts asynchronous
work into the production transaction. Parent observations bind the real PID,
SIGKILL exit, ordered SQL boundary hashes, timestamps and recovery window.
Before-commit/after-write crashes must preserve the entire old schema and rows;
after-commit crashes retain that committed migration stage and finish on restart.
There is no assertion that earlier successfully committed stages roll back.

Real SQLite query_only causes READONLY (8). A real aborting SQLite trigger causes
constraint failure (19) after the migration has already issued schema changes.
Both prove rollback of the failed stage. The constraint case's exact pre-upgrade
backup, identified by byte digest and complete original projection, is uploaded
through the application's existing HTTP validate/preview/commit flow and then
queried and edited. This is the same file from the failed upgrade, not a separate
successful restore demonstration. Additional old v1/v6/v10/v11/v12 backups use
the same HTTP path. The unchanged original backup is checked afterward.

The backup is a closed SQLite copy made before upgrade, matching the README's
manual backup requirement. There is no automatic startup-backup promise. Never
copy only a running WAL database file: stop Hearwise or use the existing export
entrypoint first. Restore through Settings/Data import with replace preview;
review its replacement effect, then explicitly confirm. Imported unfinished work
requires a deliberate retry with a key; restoration itself must not call a
provider.

The deliberately broken early-COMMIT preload actually commits partial migration
work, then kills the process. The preservation oracle must detect that change.
Additional controls reject missing scenarios/schema, altered source text, lost
paid attempts, erased boundary records, false schema versions and swapped failed
backup identities. Passing cached booleans cannot replace raw SQLite/API evidence.

## Isolated install, evidence and limits

A local source-only Git clone checks out the exact original SHA. It starts with
no build or node_modules, runs its own locked npm ci, check:version, build and
npm start (including prestart). It has a temporary HOME, explicit empty npm user
configuration, an allowlisted environment without inherited keys, a counted
loopback rejecting provider and a SQLite path outside the checkout. It checks
missing-build module diagnostics, an explicit missing-key API error, served
version, compiled SHA/dirty metadata, clean history and zero provider calls.
Then a real v11 database is upgraded, dependencies/build are removed and
reinstalled, and npm start rebuilds while all external business data remains.
Every server is a separately terminated process group.

Artifacts retain commands, complete exit/signal/timeout results, source hashes
at both ends, raw database/API observations, provenance, npm/Node/SQLite/OS/CPU,
installer logs and negative controls. The release reader requires unchanged clean
source, complete artifacts and matching current runtime. It is an original-path
local reader: cwd must be the actual Git root and the report directory must match
the real directory being read. Moved CI artifacts remain inspectable but do not
claim to pass that original-path local check. Missing, stale, interrupted or
incomplete evidence cannot pass. The runner evaluates provisional observations, then atomically writes a finalized report; the public reader rejects a missing final marker or completion/summary fields that differ from its raw recomputation. Fully observed assertion failures are failed;
missing observations/timeouts are incomplete. Installation and migration outcomes
remain separate.

The executed scope is Linux x64 and the recorded Node 24/SQLite versions. macOS
Intel/ARM, Windows, Linux ARM and other runtimes are not_run. Browser microphone,
speaker, mobile/background audio and real devices are not_run. Disk-full, kernel
crash, storage-controller failure and real power loss are not_run. Building or
serving HTML does not establish audio acceptance or broaden platform support.

## Current-source CI aggregation

The release gate requires the dedicated install-upgrade job and exactly one report
attempt. Its thin adapter reuses the same raw evaluator and finalized-summary
checks. It derives the expected original repository from the actual Git root and
the original capture directory from the checked-in job's fixed
`verification-evidence/upgrade/run-*` convention, never from fields in the report.
This permits the CI artifact download layout within the same checkout origin;
it is not an arbitrary cross-machine origin override. The original local reader
still requires the real capture directory. Other platforms and physical failure
classes remain not_run, and this technical slot does not close the umbrella
business or external upgrade-support acceptance requirements.
