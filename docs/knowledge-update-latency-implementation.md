# 知识条目及时更新：技术方案与审查

日期：2026-09-28。基线：`79a15e8`。状态：设计与实现审查通过，已完成实施和本地验证。

## 1. 目标与现状

知识仍从最终 ASR 原文抽取，遵守精选收录、证据校验、重复提及不重写正文的规则。改善从「最终句入库」到「知识卡片更新」的等待，并让用户看见整理与重试状态。

当前延迟来自三处：不足 3 句固定等 10 秒；翻译繁忙时知识任务可再等 15 秒；全服务只有一个抽取执行者。前端在收到 `knowledge-upserted` 后立即更新，但尚未组批的原文没有计入处理中，停止后的轮询遇到一次网络错误即终止。

## 2. 调度规则

| 项目 | 默认值与规则 | 取舍 |
| --- | --- | --- |
| 短暂合批 | 最后一个最终句后 1.5 秒 | 孤立句更早处理，相邻短句共享调用 |
| 合批期限 | 从本轮首个未入队最终句起最多 4 秒 | 后续句子不能不断延后截止时间 |
| 立即成批 | 3 句或累计 1200 字符；停止/断线/继续处理时强制入队 | 较完整内容及尾句尽快进入处理 |
| 批次大小 | 沿用每次最多 3 句/2500 字符；未执行的相邻任务可合并到 6 句/2500 字符 | 模型慢时积压合批，不丢原文 |
| 调用间隔 | 同一收听的任务启动间隔至少 2 秒 | 避免模型很快时短句造成调用突发 |
| 翻译让路 | 知识任务创建后最多让路 1.5 秒；翻译繁忙时按一个知识任务派发 | 保护实时字幕，同时避免知识持续饥饿；已启动请求不取消 |
| 并发与顺序 | 全局最多 2 个知识任务，不同收听轮流获得机会；每条收听最多 1 个 | 一个慢会话不独占服务，同一会话保留因果顺序 |

`EXTRACTION_WAIT_MS` 保留为翻译让路时间，默认从 15000 调整为 1500。`EXTRACTION_CONCURRENCY` 可设置为 1–4，默认 2。其他阈值集中在调度模块常量中。

合批期限、翻译让路和启动间隔是调度约束，不能保证模型完成时间。没有同会话积压、可用执行槽且无需重试时，从首个最终句到首次请求的调度等待目标不超过约 5.5 秒；孤立句且翻译空闲时通常为约 1.5 秒。跨会话高负载和模型耗时必须通过日志另行衡量。

## 3. 状态与持久化

- 新增 `knowledge-queue.mjs`，集中管理合批计时、启动间隔、公平轮转、会话锁及重试唤醒。时间、定时器与模型执行回调可注入，测试使用确定性的时钟。
- SQLite 升为版本 3，仅给 `extraction_jobs` 增加 `retry_at`。任务重试沿用 `pending`，等待时间跨重启保留；`running` 在启动时恢复为 `pending`。API Key 仍仅在内存中存在。
- `createExtractionJob` 只能合并从未启动的 pending 任务，防止把新原文并入失败重试任务。强制入队要循环排空所有未入队原文，包括因字符上限而不足 3 句的批次。
- 同一收听的最早 pending 任务在等待重试时，后续任务保留顺序；其他收听可以使用空闲槽。耗尽重试后保留失败状态，后续任务继续执行。
- 手动「继续处理」只重置 failed 任务，不能把仍在执行的任务改回 pending；重置尝试次数时将 `retry_at` 置为当前时间，仍禁止与新句合并。服务重启的恢复由构造函数负责。
- 删除收听时移除计时器；在途任务完成前再次检查记录是否存在，避免重建已删除的数据。

## 4. 失败恢复

| 失败 | 处理 |
| --- | --- |
| 网络错误、超时、HTTP 408/429/5xx | 总计最多 3 次尝试，基础退避 2 秒、8 秒 |
| 整体响应无法解析/协议错误 | 最多 2 次尝试；保留逐条校验，单条拒绝不重试整个批次 |
| 401/403/其他明确参数错误 | 直接保留 failed，用户修正设置后手动继续 |
| Retry-After | 接受秒数或 HTTP 日期；不早于服务指定时间重试。超过 5 分钟则终止自动重试并保留失败 |

429 退避期间对使用同一 API Key 的知识任务施加内存冷却，避免多个会话同时反复触发限流；翻译调度独立。等待重试不占执行槽。每次执行有 30 秒请求超时，保留已有分片和落库幂等规则。

## 5. 页面反馈

详情接口和 `processing-updated` 事件提供最新的翻译与知识处理计数，知识部分包含未入队句数、排队、执行、等待重试和失败任务数。

- 收听中显示「知识整理中」或「知识稍后自动重试」，未组批的原文也计入处理中。
- 自动处理正在运行时，不要求用户反复点「继续处理」；失败或缺少内存 Key 时保留操作入口。
- 实质内容更新仍由 `knowledge-upserted` 立即推送；任务完成后拉取详情，补齐仅追加引用等不触发卡片高亮的变化。
- 停止后立即查询一次，仍有后台任务时每 2 秒补齐；详情请求 10 秒超时，网络错误延后再试，避免单次错误永久停更。每轮等待上轮完成，切换记录或重新开始收听会取消旧轮询结果的后续调度。记录已删除时停止查询。
- 从历史页重新打开仍在后台处理的记录时恢复轮询。

## 6. 可观测性

记录 `knowledge_job` 结构化日志：任务/收听 ID、尝试次数、状态、批内句数、排队时长、本次执行时长、从首/末最终句到完成的时长、重试等待。重试的 `queue_ms` 从重新排队时计时（含退避），`job_age_ms` 保留从最初创建至今的总时间。日志不含 API Key 或原文。

比较优化前后时，应区分 ASR 定稿耗时、调度耗时、模型耗时和停止后的轮询延迟。优先观察调度等待的 P50/P95、积压任务数、失败率及每分钟调用量，不能将模拟模型的耗时当作线上模型性能。

## 7. 设计审查

| 审查点 | 结论与约束 |
| --- | --- |
| 连续输入会不会无限延迟 | 首句期限固定，3 句/字符阈值可提前触发 |
| 模型慢时会不会并发更新同一对象 | 同一收听持有执行锁，后续请求在前次落库后读取最新候选 |
| 会不会因降延迟扩大费用 | 1.5 秒合批、2 秒最小启动间隔、积压合并和并发上限共同约束；稀疏句子的调用量仍可能高于旧方案 |
| 会不会阻塞字幕 | 翻译保留原有并发；繁忙时知识并发收为 1，短暂让路后仍获得执行机会 |
| 重试会不会改变输入范围或重复建条目 | 重试任务不再合并新句；依靠现有唯一键、稳定对象 ID 与事实去重保证重复执行 |
| 手动重试重置次数的影响 | `attempts=0` 不能单独代表从未执行，合并还要求 `retry_at IS NULL` |
| 停止后立即继续的调用频率 | 释放 Key 时保留尚未到期的 2 秒启动间隔；冷却表清理不再被引用的 Key |
| 新一轮麦克风/标签页采集失败 | 恢复原记录的后台轮询，不因启动失败而永久停止补齐 |
| 长句/停止时是否遗漏尾句 | 强制入队循环到没有未覆盖句，不以「恰好 3 句」作为继续条件 |
| 重启与 Key 丢失 | pending/running/retry_at 持久化；无 Key 时显示需要继续处理，不伪称正在运行 |
| 状态是否引起额外全量请求 | 普通状态事件只更新计数，任务结束才补齐详情 |
| 选择性收录是否受影响 | 不改提示词的收录阈值、ASR 断句或对象身份合并规则 |

审查结论：方案可实施。上线性能仍需真实模型记录验证；本轮用可控模型与确定性时钟验证延迟边界、顺序、公平性、失败恢复和事件送达。

## 8. 实施验证

- `npm test`：47 项通过，其中新增 25 项覆盖时钟调度、并发/公平性、重试、数据库迁移、真实 HTTP/WebSocket 链路及前端状态与轮询。
- 单句最终原文在保持收听连接时触发抽取；本地模拟模型首次请求约在最终句后 1.52 秒发起。首次返回 HTTP 429 后约 2.02 秒自动重试，成功写库并推送卡片。
- 翻译请求持续占用时，3 句知识任务约在最后最终句后 1.51 秒发起，知识先于被刻意阻塞的翻译结果完成。
- 已验证失败重试不合并新句、同会话不并发、不同会话公平派发、重启保留重试时间、v1/v2 数据库迁移、删除与迟到结果、网络恢复以及已有知识协议的幂等行为。
- 审查中修正了手动重试导致批次合并、读取模型响应体超时被误归类、释放 Key 后调用间隔丢失、采集启动失败后轮询未恢复的问题。
- JavaScript 语法检查和 `git diff --check` 通过。

以上是模拟模型和本地状态机验证，尚未测量真实千问模型的延迟、额度或长期调用费用；真实卡片完成时间仍包含模型耗时，稀疏讲话的调用量可能增加。全局知识并发在翻译开始繁忙时只限制后续派发，不取消已经启动的请求。

数据库 v3 为增加一列的迁移。完整回退到只支持 v2 的旧程序需同时恢复升级前数据库备份；仅回退调度逻辑时应保留 v3 存储兼容代码。
