# 临时译文参数报错与恢复方案

## 背景与目标

`POST /api/translate` 拒绝超过 3000 个 UTF-16 code units 的文本，但前端持续提交未结束句，没有长度保护。最终句使用独立翻译队列，因此可能出现「翻译参数无效」与正常最终译文同时显示。错误提示在成功后没有清除。以上行为已用模拟 ASR、翻译服务复现；用户实际失败请求尚未取得，不能认定只有文本超限这一种原因。

本次从 main 独立修复，与知识及时更新 PR #10 分别提交，不更改最终译文、原文持久化、知识抽取或数据库结构。

## 行为约定

| 场景 | 行为 |
| --- | --- |
| 临时文本 trim 后长度为 5–3000 | 按现有 1200ms 间隔发送最新内容；不足 5 的文本继续等待识别 |
| 临时文本超过上限 | 取消旧请求及待发定时器，保留已有临时译文，提示「长句识别中，等待完整译文」；不截断原文、不发送超限请求 |
| ASR 修订文本后重新符合上限 | 恢复临时翻译 |
| 最终翻译队列忙碌（429） | 中性提示「最终译文优先处理中」 |
| Key、文本、语言值不合法 | 返回稳定错误码、字段及可读原因；API 不返回请求文本或 Key |
| 网络/模型等实际失败 | 标明「临时译文暂不可用」，最终翻译继续处理 |
| 临时译文恢复、新句或最终句到达 | 仅清除属于临时译文的提示，不抹掉连接、音频采集等错误 |
| 旧句/旧连接的请求迟到 | 取消并通过版本校验忽略，包括迟到的 429、错误与成功响应 |
| 保存空白 Key | 校验后再更新内存及 localStorage；无效输入保留原 Key，使用表单校验提示 |

## 实现

- 新增浏览器与服务端共用的临时翻译参数规则模块，统一长度与语言枚举；trim 后计长，维持原来的 JavaScript 字符串计量方式。
- API 对格式、Key、文本、源语言、目标语言分别返回错误码；保留 `error` 字段兼容现有客户端。
- 前端在调度前处理文本超限，在实际请求前复核参数，防止定时器等待期间参数变化。
- 提示记录来源；临时翻译错误不能覆盖其他错误，恢复时只清除自己产生的提示。
- 新句、最终句、断线与 Key 更新时取消过期临时请求；所有响应先校验版本，再更新提示或字幕。

## 方案审查（实施前）

- 保持原文完整，超长最终句仍进入既有翻译队列；不以截断临时文本制造内容完整的错觉。
- 保留请求长度上限，避免一次扩大模型调用量或引入分块翻译顺序问题。
- 3000 是本应用的临时接口限制，不视为上游模型的长度保证；最终模型仍可能按原逻辑失败。
- 长句超过上限后，临时字幕会暂停刷新，等待最终译文。这是明确的降级行为。
- 并发风险不仅涉及成功响应，也涉及 429 与错误；版本检查必须在所有 UI 分支之前。
- 成功不应清除无关错误；Key 无效时不得先覆盖现有凭据。

审查结论：按以上约定实施，并使用以下回归场景验收。

## 验证计划

1. 临时接口边界：3000/3001、首尾空白、空 Key/文本、非法语言、非法 JSON/请求结构。
2. 前端超限不请求、保留已有译文、取消排队/在途请求，文本缩短后恢复。
3. 错误后成功及最终句到达清理对应提示；其他错误不被覆盖或清理。
4. 跨句、最终句之后及取消后的旧成功/429/失败不回写界面。
5. 空白 Key 保存保留旧值，有效输入恢复表单可提交状态。
6. 真实本地 HTTP/WebSocket + 模拟 ASR/模型：超长临时输入被明确拒绝，最终句完整入库并翻译成功。
7. 运行仓库测试、语法检查与 diff 检查，不调用真实付费模型。

## 实施与验证结果

- 实施上述方案；额外防止空成功响应把原文误标为临时译文。
- 新增 16 项回归测试（13 项实际前端脚本/事件处理器测试、3 项本地 HTTP/WebSocket 集成测试），覆盖上述边界及迟到的 200/400/429/502 响应。
- `npm test`：38 项通过、0 项失败；JavaScript 语法检查及 `git diff --check` 通过。
- 模拟完整链路确认：3001 字符的临时请求返回 `INTERIM_TEXT_TOO_LONG`；同一完整原文作为最终句进入翻译模型、保存完整原文及成功译文；繁忙状态解除后临时接口恢复。
- 前端测试执行真实 `app.js`，使用简化 DOM、受控定时器及模拟网络；未进行浏览器视觉检查，也未调用真实付费模型。上游模型的实际成功率与延迟不由这些测试保证。
