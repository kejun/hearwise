# 编辑协议验证（KEJ-69）

本目录验证手动名称纠正的并发修订、事务原子性和保存不确定性。性质 ID 为 HW-06-06、HW-06-07、HW-11-04；现有 KEJ-68 的 HW-06-02 至 HW-06-05 保持不变。

## 运行和判定

使用当前 checkout 的锁定依赖、Node 24 和 Java 21：

```bash
npm ci --ignore-scripts
npm run setup:relation-protocol
node scripts/verify-edit-protocol.mjs --release
node scripts/verify-edit-protocol-report.mjs RUN_DIRECTORY --release
```

复用 `scripts/lib/relation-protocol-tools.mjs` 的 Quint 0.33.0、Apalache 0.62.1、TLC 1.8.0 校验与缓存；不安装另一套工具。TLC 来自已校验 SHA256 的 Apalache JAR。每次工具运行使用独立本地服务端口、单项超时及进程组清理。整体预算为 480 秒，TLC 每项 60 秒，Apalache 每项 120 秒。未完成必须失败退出，不能提高预算消除超时。

运行器保存源码 SHA、工作区状态、模型及锁文件哈希、环境、工具版本、命令、时间、退出码、日志、ITF 和逐步实现观测。门禁从当前版本的计划及原始文件重新判断，拒绝缺失、重复、过期、修改或中断的证据。发布证据还要求已提交、干净的源码。每个 `ok` 只适用于声明范围。

`report.ok` 不是 KEJ-69 或整个 KEJ-61 的独立完成依据。此运行器的客户端状态是协议抽象；真实浏览器草稿、焦点、按钮和后续操作必须另有同性质证据。报告明确保留 `browserAcceptance: requires_separate_actual_browser_evidence`。

## 有限域

- `two_current`：同一条目，两个客户端，均为当前 v1 修订。
- `two_legacy`：同一条目，客户端分别提交冻结 v11、v12 修订。
- `v11_override`：一个 v11 客户端；初始名称覆盖字段非空，因此其旧 token 不合法。
- 每个客户端最多一次明确的保存操作；模型负例才允许自动多发一次。
- 名称域为 Deebo、Tibo、Mira。允许无变化保存：成功回执仍创建，但修订和通知保持不变。
- 初始关联片段译文为 failed/null，允许一次真实 `setTranslation` 完成；它改变修订，不改名称或保存回执。
- 每次事务允许成功或中途失败，通知允许正常或抛错，响应允许成功送达、丢失或代理 502，回执读取允许成功或不可用。
- 关闭和重新打开可反复发生，但不会扩大保存次数；修订值是实际内容指纹变化的有限身份编号，不是假造的数据库版本字段。

所有配置的 TLC 都必须完整探索相同的声明有限域。开发测量中 `two_current` 与 `two_legacy` 各产生 1,623,466 个状态、341,143 个唯一状态、队列剩余 0、完整图深度 24；`v11_override` 产生 1,252 个状态、398 个唯一状态、队列剩余 0、图深度 13。运行时间约为 23、21、8 秒，包括编译与启动。这些是开发成本测量，不是最终源码的发布结果；未来模型变化后必须重新运行。TLC 指纹碰撞概率估计保留在原日志中。

## 有界检查成本

首次候选深度 8 在 120 秒预算内没有完成；逻辑等价的布尔包装优化也超时，随后被撤销。两个完整原始日志及摘要保存在 `docs/edit-protocol-cost-probes/`，状态均为 incomplete，不计通过。它们不属于 fast 的通过清单。

当前双客户端深度 6 实测约 51 秒后完成，随后冻结 fast 的三个正向配置为最大深度 6。TLC 状态域、断言和长路径见证没有缩减。通过 fast 只说明 Apalache 在 6 步内未发现违反；不代表候选深度 8 通过，更不构成归纳证明。长交错路径由完整 TLC、确定性见证和实际实现重放分别提供证据。

模拟固定 TypeScript 后端、seed 2026101469、每配置 100 样本、最多 24 步，保存每配置 3 条轨迹。确定性见证 seed 为 69，包含当前版本 11 条、旧版 2 条、v11 覆盖字段拒绝 1 条，共 14 条。随机模拟不能代替固定验收见证。

## 动作和真实边界

精确动作、枚举和投影合同位于 `verification/edit-protocol/trace-contract.json`。

1. `read/edit/send` 分离读取、用户编辑和网络提交。发送冻结实际 revision token 与名称；实际 POST 计数与用户保存次数独立观测。
2. `transaction` 调用实际 `replaceKnowledgeName`。SQLite 的 `BEGIN IMMEDIATE`、事务内修订校验、关联业务写入和回执提交是一个同步原子边界。失败观察整个业务投影回滚，不是只检查名称。
3. `notify` 单独观察提交后的真实通知。`serverOwner` 保证事务和同步通知之间不插入另一个 HTTP handler 的写入或读取。它们不是网络发送的同一个原子动作。
4. `deliver/lose_response` 控制已经产生的真实 HTTP 响应。晚到见证先保持 A 的成功响应，再让 B 读取并保存更新，最后交付 A；A 的刷新必须读到 B。
5. `lookup` 仅查询 `/edits/:id`，绝不再次 POST。已提交但响应不可知时可以恢复成功；查询不可用则保持 unknown 与原输入。
6. `refresh_stale` 读取最新内容，保持草稿和 POST 次数；只有新的用户操作才可授权后续提交，该后续交互由浏览器证据覆盖。
7. `close/reopen` 关闭可关闭状态并重新查询实际持久内容。失败输入保持的承诺针对尚未关闭的对话框；本模型不承诺持久保存本地草稿。

真实 HTTP 适配器通过测试用子进程预加载记录实际存储和通知检查点；阻塞门闩只用于测试进程，不增加生产调试端点。正常 SQLite 查询和真实 HTTP 结果提供持久投影。模型 expected 永远来自 Quint ITF；驱动不根据实现重新生成 expected。

前端真实限制必须保留：手动 POST 期间 busy=true、polling=false，关闭按钮禁用，close() 无效，Escape 被阻止。允许关闭的是空闲、失败、未知状态，或旧版任务轮询阶段。因此本模型没有“用户关闭一个忙碌的手动 POST 后仍收到 fetch 成功回调”的虚构路径。取消见证取消尚未发送的草稿。`closedPhase` 只检查关闭后的阶段，不宣称单独证明名称、修订、回执或请求计数不变。`close` 动作以记录更新的 frame 保持其余状态；取消可达见证另外核对零请求、原名称、原修订和无回执。真实浏览器还需比较关闭前后的全表与写入计数。

同一客户端失败后再次明确点击保存属于可继续操作的浏览器验收；它不在每客户端一次保存的 TLC 域内，不能从此模型通过推导。

## 冻结兼容和负例

适配器必须通过真实 `knowledgeRevision` 和独立冻结夹具 `preFixRevision(snapshot, 11|12)` 生成提交 token；不能用模型的整数直接代替 HTTP 修订。v11 在任一覆盖字段非空时被拒绝。此模型不声称旧 token 具有当前规范化的排序、时间戳不变性；这些由 KEJ-68 的证明与兼容测试处理。

两个模型变异分别绕过事务版本校验、以及冲突读取新修订后自动 POST。单客户端加一次后台修订变化已足以产生真实前提，最短预期反例分别为 5 和 8 步。必须检查 ITF 中确实违反 `revisionCheckedInTransaction` 或 `noAutomaticOverwrite`；解析错误、未安装工具或超时不能算检出。

两个实现负例从正向 `backgroundConflictTest` 轨迹出发，分别执行测试隔离副本中的真实版本校验变异，以及额外真实 POST。结果必须为 `implementation_mismatch`，保存第一次不同的状态前缀。该前缀只是在当前轨迹中的首次差异，不声称是全局最短反例。无法执行和清理失败报告为 `unreplayable`。

Quint 0.33.0 的 TLC 后端不导出 ITF；完整 TLC 原日志提供有限域检查证据。确定性测试、模拟和 Apalache 反例导出 ITF，再由独立编辑 normalizer 解码并逐步重放；已有关系协议驱动未改动。
