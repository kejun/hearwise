# 知识条目优化：阶段 1 技术实现

状态：实施依据（2026-09-28）。产品规则见 [优化方案](knowledge-items-optimization-plan.md)。本轮目标是精选收录、同一收听内稳定去重、可追溯的增量补充及卡片简述；阶段 2 的「当前相关」双层界面、归并/拆分、按需背景生成和自动加载引用不在本轮。

## 需求澄清与取舍

| 问题 | 本轮决定 |
| --- | --- |
| 实施范围 | 阶段 1；先建立可评估的收录质量，再考虑丰富的阅读界面。 |
| 交付 | 独立分支上的草稿 PR，不直接更改 `main`。 |
| 收录对象 | 具体且对当前内容重要、解释有用的人物、组织、产品、作品、特定方法/理论、独立事件或地点。频率和陌生程度都不能单独触发收录。 |
| 泛词 | `AI`、人工智能、互联网等完整泛称默认排除；`OpenAI` 不因子串包含 `AI` 被排除。 |
| 待观察 | 保存有潜力但尚不足以收录的对象和原句；不出现在知识列表。明显泛词不要求保存。 |
| 同名冲突 | 仅凭名称相同不合并；缺少身份依据时保留内部候选。已有目标 ID 无效时不降级为正式新建。 |
| 更新 | 重复提及只增加不重复的引用；有新信息才写入有来源的增量并刷新卡片。明确更正仍使用现有名称修订约束。 |
| 历史记录 | 原有记录沿用 v1 协议和数据；新记录固定使用 v2。继续收听、失败重试和服务重启不能改变记录的协议版本。 |
| 长样本 | 仓库尚无经人工标注的两小时样本。本轮提交固定行为测试和可复用回放方法；方案中的 90%/95% 目标须等真实标注集测量，不能仅凭单例宣称达到。 |

## 现状与风险

`storage.mjs` 中的 `knowledge_items` 保存单句摘要，`applyKnowledge` 每次匹配都覆盖摘要并发送更新；名称检索仅将本批字符串与最多 6 条最近条目匹配。`knowledge.mjs` 的 v1 协议偏向人物、术语、事件，证据可追溯但只校验引用字符串存在，不校验摘要每个事实都被引用支持。`server.mjs` 的队列与翻译优先规则可以继续使用。前端重建卡片时恢复了展开状态，但折叠时看不到内容说明。

最关键的风险是过度抽取、同名错合并和新摘要覆盖旧解释。服务端应在模型之后保守校验；无法验证身份的模型 `update` 不得转成 `create`。对摘要与证据的语义一致性仍需人工样本评估，字符串校验不能证明陈述真实。

## 数据迁移与版本

数据库从 `user_version=1` 升为 2，迁移在事务中执行；旧 `listenings` 的 `knowledge_policy_version=1`，新收听为 2。`extraction_jobs.prompt_version` 从所属收听复制，不再硬编码 1。v1 待处理任务仍用原提示词与解析器；原 `knowledge-extraction-prompt.md` 保持不变。

新增 `knowledge_candidates`（收听 ID、候选 ID、名称/规范化名称、类别、`observe|exclude`、理由、身份线索、首末句 ID 与时间）；新增 `knowledge_facts`（条目 ID、简短增量、原文句 ID 和引用、确定性、创建时间），对相同条目/句/内容建唯一约束。`knowledge_items` 增加 `display_label`、`short_description`、`policy_version`、`content_version`，旧条目用原摘要生成简述。候选和增量通过外键随收听删除。背景仍按旧字段展示，本轮 v2 不要求模型生成背景。

`content_version` 仅在名称、正文增量、简述发生实质变化时增加。新引用或重复提及不增加版本，也不触发「已补充」。任务完成与写入的事务边界应确保重试不会重复插入候选、条目或细节；现有批次以句 ID 和唯一约束实现幂等，处理一批内拆分时每部分独立写入。

## v2 模型输入与输出

输入沿用 `focus_segments`、完整的近期 `context_segments` 和 `existing_candidates`，增加按本批名称召回的 `observed_candidates`、简短主题上下文和 `policy_version=2`。上下文仅用于消歧，正式新对象必须由本批原句支持；待观察候选可用先前被授权的原句作为补充证据。检索先用同场名称/别名和近期上下文，不引入向量库；明确的同名歧义宁可暂缓。

输出 `{"items":[...]}`，每项含 `action`（`create|update|observe|exclude|repeat`）、`type`（兼容现有四值）、`display_label`、`canonical_name`、`role`、`reason`、`existing_item_id`、`observed_candidate_id`、`aliases`、`short_description`、`new_information`、`certainty`、`evidence`。`create` 需要三项收录条件、当前原文证据与简述；`update` 需当前收听内有效目标 ID 和新事实；`repeat` 只追加证据；`observe` 保留候选与依据；`exclude` 可记录精简原因。允许空数组，不设最低条数。单次最多 12 个决策，但此上限不得让重要对象永久消失；超过上限时应拆分并记录需要复查的批次。

解析器逐项校验字段、受支持 ID、原文逐字引用与操作语义。泛词只按规范化后的完整名称过滤，不对 `OpenAI` 等子串误杀；数字/价格属性不能建条目。服务端只把合法 `create` 变成正式条目；不合法 `update` 和 `repeat` 进入待观察或拒绝，绝不静默新建。`new_information` 逐句绑定原文证据，保留「我记得」「可能」「计划」等语气；没有明确新增信息则作为 `repeat`。摘要是否受证据充分支持仍通过样本评审。

## 服务端写入与界面

先尝试有效 ID 对齐，再查已确认的规范名称/别名和对应原文；同名有多个对象时暂缓。新对象记录短说明和第一条可追溯信息；已有对象仅在确实有新内容时插入事实。待观察候选的后续出现按 ID 或同名及上下文召回；提升为正式条目时保留其早期原句。已排除的名单对象以后成为主体时允许重新判断。每次写入后返回发生正文变化的条目；只增加引用的条目可静默同步。

前端折叠卡片显示名称、具体类别与一句说明，展开继续显示原文相关信息和引用；旧条目用 `dialogue_summary` 回退显示。保持稳定收录顺序及展开状态。`knowledge-upserted` 仅在新增或实质更新时广播。背景补充仍与对话内容区分。

## 测试与验收

用无真实 API Key 的模拟模型测 K01–K14、K19–K21：柯达只建公司和相机；泛词零泄漏，`OpenAI` 可按角色判断；赞助商名单先待观察；后文提升并保留早期证据；跨批别名匹配、不合并同名食物；重复任务不增条目/事实/版本；结尾未满三句也要处理。覆盖 v1 历史和未完成任务、v2 新记录的重启与重试、删除级联、字幕延迟不被知识处理拖慢。

评估脚本按时间顺序逐批回放标注样本，输出准确率、关键对象覆盖率、重复率、错合并、泛词泄漏、证据可定位率、呈现延迟和调用量。对两小时长样本的人工标注和指标测量是上线前的独立验收门槛；没有样本时 PR 只能说明行为测试通过，不能声称达到方案阈值。

## 后续阶段的接口边界

阶段 2 可读取 `knowledge_facts`，增加细节折叠、相关对象和原文按需定位；「当前相关」只改变视图排序，不复制实体。对象归并、拆分和新的整理版本需独立事务与恢复记录，本轮不会把简单的名称匹配伪装成完整身份管理。阶段 3 的用户反馈、外部核实与跨收听关联须分别评估。
