## 2. 输出契约：分类只保留一个必填来源

### 2.1 模型给 display_label，服务端派生 type

新 v2 提示词不再要求模型同时选择两套分类；数据库和前端继续保留现有 type。

| 模型 display_label | 服务端存储 type |
| --- | --- |
| person | person |
| organization | other |
| product | other |
| work | other |
| method | term |
| event | event |
| place | other |

在 `knowledge.mjs` 定义唯一映射常量。标签经过外围空白清理后必须命中枚举；不猜测未知标签、不根据名称推断分类。

兼容旧输出：type 缺失时派生；type 与派生值一致时正常接受；type 等于合法 display_label 时（例如 organization/organization）按明确的同义填法归一化并记录 `TYPE_DERIVED`。除此以外的 type 值一律返回 `TYPE_LABEL_CONFLICT`，包括 person/organization、term/product、other/person、null 或未知字符串；交给纠正，不静默掩盖冲突。

已有目标仍按真实 ID、类型和 display_label 校验。派生类型不能让组织更新到人物，也不能把两个同名对象强行合并。v1 输入和解析协议继续保留。

### 2.2 把实际限制写进运行提示词

保留最多 12 项、响应长度上限 30000 字符；明确每条 quote 不超过 300 字符，必须属于本次 focus 的真实 segment_id，是连续原文片段。超过限制时选择更短且完整支持陈述的片段，必要时提供多处证据；服务端不截取长引文的前 300 字冒充完整证据。

明确 create/update 必填 short_description 和 new_information；repeat 只追加提及；observe 表示身份或作用仍待观察；exclude 表示不符合收录范围。已有目标 ID 只能从输入候选选择。名称、说明、增量内容等长度限制与当前代码保持一致并写清楚，不再依赖模型猜测。

提示词提供一个组织创建和一个已有条目更新的完整 JSON 示例，使用通用案例；用户新闻原文留作评估样本，避免把答案写进生产提示词。给协议增加内部 `contract_revision`（拟为 `v2.1`），用于日志与检查点识别；它不同于收听策略版本和数据库版本。

### 2.3 归一化边界

允许外围空白清理、上述确定性类型转换、重复别名/引用去重，以及现有引号、空白、大小写容错后回填原文子串。沿用有依据的别名过滤。

禁止自动补写事实、说明、角色、理由或 certainty；禁止按名称猜目标 ID、自动将 update/repeat 改为 create、放行改写引用或历史句证据。纠正模型可以重新提出 action，但必须重新通过完整校验和存储身份判断。

## 3. 可诊断的逐项校验

建议解析接口：

```js
{
  returnedCount,
  accepted: [{ sourceIndex, item }],
  rejected: [{ sourceIndex, name, issues: [{ code, path, details }] }],
  normalized: [{ sourceIndex, code }],
  evidenceWarnings: [{ sourceIndex, code, evidenceIndex }]
}
```

| 检查 | 错误码示例 |
| --- | --- |
| 基础字段 | ACTION_INVALID、LABEL_INVALID、TYPE_LABEL_CONFLICT、NAME_REQUIRED、ROLE_REQUIRED、REASON_REQUIRED、CERTAINTY_INVALID |
| create/update 内容 | DESCRIPTION_REQUIRED、NEW_INFORMATION_REQUIRED |
| 已有对象 | TARGET_REQUIRED、TARGET_UNKNOWN、TARGET_LABEL_MISMATCH |
| 待观察对象 | OBSERVED_TARGET_UNKNOWN、OBSERVED_LABEL_MISMATCH |
| 证据 | EVIDENCE_REQUIRED、SEGMENT_NOT_IN_FOCUS、QUOTE_EMPTY、QUOTE_TOO_LONG、QUOTE_NOT_VERBATIM |
| 收录边界 | BROAD_NAME、NAME_NOT_IN_FOCUS |
| 纠正响应 | REPAIR_ID_UNKNOWN、REPAIR_ID_DUPLICATE、REPAIR_ITEM_MISSING、REPAIR_IDENTITY_CHANGED |

同项收集相互独立的错误，避免缺少前置字段引起无意义的连锁报错。多条引用中保留有效引用，丢弃的引用单独记录；非 exclude 至少需要一条有效证据。字符串匹配只能证明引用可定位，不能证明陈述语义完全被引用支持，后者仍需模型评估与人工核对。

当前 `applyKnowledgeV2()` 只返回 changedItems，应增补逐项实际处理结果：created、updated、repeated、observed、excluded、deferred_identity。deferred_identity 表示存储层因身份歧义暂存观察，不算写入失败，也不算已显示卡片。调用方能区分「解析通过」「暂存候选」「真正上屏」。

计数口径固定如下：created 指实际新增对象；updated 指已有对象实际新增事实、合法更名等可见内容变化；update 但事实全部重复时归为 repeated/noop，不增加内容版本或 updated_count。只增加引用也不算正文更新。visibleChangeCount 按一个处理周期内真正改变可见内容的唯一卡片 ID 去重，多项更新同一对象只算一张；deferred_identity 不计入该值。另分开记录 accepted_initial_count（首次解析通过的 sourceIndex 数）与 resolved_count（最终已处理的 sourceIndex 数），纠正成功只增加后者，不能修改首次通过率的分母。

## 4. 有效项先保存，拒绝项定向纠正一次

对每个现有 `splitFocusSegments()` 分片执行：

1. 读取原分片和最新候选，进行首次抽取、归一化和校验。
2. 在一个 SQLite 事务中应用有效项、记录逐项结果及未解决项、推进分片检查点。事务提交后立即广播 changedItems，不等待纠正。
3. 首次输出 `items=[]` 且没有校验错误时，正常结束该分片；observe/exclude/repeat 均是有效决策，也不因没有新卡片而重试。
4. 有拒绝项时，先持久化一次纠正额度，再发送一次定向纠正请求。
5. 纠正返回后逐项重新校验，将通过项及其检查点一并提交、广播；保留未解决项。纠正失败不重新执行已成功部分。
6. 当前分片终结后处理下一个分片；当前任务终结后让同一收听的后续任务继续。

纠正输入包含：原分片 focus、原来用于解释的有限 context、入库后刷新的 existing/observed candidates、被拒绝项及其字段错误。失败数据作为待分析 JSON，不作为指令。只发送拒绝项，不要求重输出成功项；保持已有的候选与原文容量边界。刷新候选应优先保留仍存在的原请求已提供目标，避免候选重排本身造成 TARGET_UNKNOWN。

拒绝项使用服务端稳定 ID，例如 `job_id/part_no/source_index`。纠正响应协议：

```json
{
  "corrections": [
    { "rejection_id": "job/0/1", "item": { "action": "create", "...": "完整 v2 条目" } }
  ]
}
```

示例中的省略符仅说明接口形状，生产提示词必须给完整合法字段。每个拒绝 ID 最多返回一次；未知 ID、重复 ID、额外实体均拒绝。

拒绝 ID 只标识位置，另持久化不可变的 `repair_anchor` 防止同位置换实体：

- 原项指向输入中的有效目标 ID，且原名称已与该目标的规范名称/已确认别名一致时，以该 ID 为锚点。纠正仍更新/重复该对象时必须保持 ID 与标签；不得换目标或以 create 绕过身份约束。
- 没有有效目标时，只有原 canonical_name 能在原 focus 中定位，才建立「该名称＋原文位置」锚点。默认不允许换规范名称；名称变化仅允许原输入已给出的、可定位的明确更正关系或已确认别名，复用现有更名约束，不接受模型新造关系。
- 对这种无目标锚点的拒绝项，纠正可以创建、观察或排除原对象；如要转成对已有条目的更新，必须存在原请求或本批已提交结果中可验证的身份关联。名称相同、仅有一个同名候选或角色相近都不是充分依据；不能确认就暂存观察或继续 unresolved。
- 原名称缺失且目标无效，或名称不能定位又无可靠目标时，不发起该项的自动纠正，记 `REPAIR_IDENTITY_UNRESOLVED`。剩余有锚点的拒绝项仍可共享一次纠正请求；不能让模型另找一个主体填进空槽。

身份锚点只锁定这次纠正针对的对象，不绕过事实、原文证据和存储层的同名歧义检查。

若重新判断对象确实不值得收录，可以返回完整的 exclude 决策及具体理由，单独统计为「纠正后排除」，不记为成功创建。无法修好、遗漏某个 ID、空 corrections 数组都不能悄悄清除原拒绝项。exclude 的语义是否合理由真实样本验收，不能用一个自由文本理由保证公司主体绝不被误排除。

## 5. 调用预算、排队和中断

### 5.1 一份自动周期预算，避免内外层重试相乘

以一个 job 的一次自动处理周期为单位，m 表示固定的原文分片数：

| 调用 | 上限与行为 |
| --- | --- |
| 正常抽取 | 每个分片一次基础请求；整个 job 共享最多两次额外请求，因此至多 m+2 次 |
| 顶层 JSON/协议错误 | 最多一次额外请求，消耗上述共享额外预算，不另外开一套重试循环 |
| 网络、超时、408/429/5xx | 消耗共享额外预算，沿用 2 秒、8 秒退避；单次请求 30 秒超时 |
| 逐项校验拒绝 | 不触发整批抽取重跑；每分片最多一次纠正 HTTP 请求，单次 15 秒超时 |
| 纠正网络错误、格式错误、超时 | 不自动再次纠正，不交给外层重跑原抽取；记录未解决后继续后续工作 |
| 401/403/确定的参数错误 | 不自动重试，保留可继续处理状态与原因 |

总自动调用上限为 `2m+2`；常见单分片、网络正常的情况为一次抽取，必要时增加一次纠正。所有本地可归一化的问题零额外调用。人工点击继续处理才开启针对未解决工作的下一周期；自动计时器、轮询、停止/继续收听和刷新页面不重置预算。

现有 `attempts` 保留为调度执行次数，另以检查点内的实际请求计数控制预算，避免服务重启或分片循环使计数含义混乱。新预算适用于 v2；v1 保留原重试规则。

### 5.2 时序约束

纠正占用当前收听的串行执行位置，每分片纠正 HTTP 最多额外占用 15 秒；m 个分片的请求耗时上限为 15m 秒，另外还有请求间隔、已有冷却和执行槽等待。有效项已在纠正前展示。先采用有界串行，避免后续条目先落库导致复杂的身份竞态；异步低优先级补偿队列不纳入本轮。

初次及纠正请求均遵守已有全局知识并发、同收听串行、同 Key 的 429 冷却；同收听的模型请求间隔至少 2 秒，纠正也计入。等待间隔或冷却时持久化 ready time，释放执行槽，不把「正常继续一个分片」算成失败重试。调度器仍选择同一收听最早的未终结 job，不能因为它释放了槽就越过它执行后面的 job；不同收听可以利用空闲槽。进入可实际发送状态时才预约请求额度。

明确改造 `execute → scheduler` 返回协议，不能沿用现有「正常 return 就 mark complete」：

```ts
type ExecutionResult =
  | { kind: 'continue'; readyAt: number; reason: 'phase' | 'interval' | 'cooldown' | 'network_retry' }
  | { kind: 'terminal'; outcome: 'ok' | 'empty' | 'partial' | 'invalid' };
```

每次执行最多发送一个模型 HTTP 请求，再按结果推进阶段。continue 在同一事务中保存检查点并保持 `pending / outcome=NULL`，调度器释放 running 槽、安排下次唤醒；不会进入完成分支。普通阶段/间隔等待写分片 ready_at，只有真正的失败退避写 job.retry_at，不混算「自动重试」。`hasWork()` 对等待继续的 job 为真，防止释放其内存 Key。只有 terminal 才聚合质量并写最终状态；v1 的 execute 返回值由适配层保留原语义。

纠正遇 429 后仍更新共享 Key 冷却，并通知调度器重新唤醒；即使不再重发这个纠正，也不能让其他任务立即冲击同一个 Key。Retry-After 使用现有解析与最长自动等待规则。已知冷却截止时间还持久化到任务，重启后约束同一收听的后续分片及任务；跨收听的同 Key 关联仍仅在内存中维护，不持久化 Key 或其标识。

因此不能承诺「1.5 秒出卡片」：1.5 秒主要是合批等待，端到端还包括模型和可能的纠正耗时。保留原正常路径延迟，明确异常路径的额外代价。

### 5.3 崩溃窗口

所有 HTTP 请求发出前持久化预算占用。纠正额度是最多一次发送机会，不承诺远端严格 exactly-once：请求前后断电时，服务端可能无法知道供应商是否处理过。

重启发现纠正额度已占用却没有已提交结果时，保留 `REPAIR_INTERRUPTED` 未解决状态，不自动重发、不标记成功。原抽取请求的中断同样消耗请求预算，只有剩余预算允许时才重发。

成功项入库与检查点原子提交：提交前崩溃两者一起回滚；提交后崩溃从检查点跳过成功部分。广播在事务后，广播丢失由现有详情查询与轮询补齐，不再次生成事实。检查点与知识写入共用事务边界，需要拆出当前 applyKnowledgeV2 的事务内实现，避免嵌套 BEGIN。

## 6. SQLite v4 与任务结果

推荐小范围增加持久化，而不是把拒绝详情塞进 last_error，或仅依赖内存 Set。

### 6.1 数据结构

- `extraction_jobs.outcome`：NULL（处理中）、legacy（历史任务未记录质量）、ok、empty、partial、invalid。
- `extraction_jobs.progress_json`：版本化内部检查点，包含 contract_revision、人工周期号、共享额外请求计数、顶层协议重试计数；不含 Key。
- 新表 `extraction_parts`：主键 `(job_id, part_no)`，外键删除级联；字段包含固定的原文引用范围、phase、ready_at、初次请求次数、纠正额度占用、未解决项 JSON、结果计数和更新时间。

原文范围保存 segment_id 与字符起止位置，使用当前切片规则，后续恢复不重新切分；不复制整篇原文。未解决项保存有大小上限的原模型条目及错误，足够用于定向纠正；不保存完整 HTTP 包、完整聊天记录或 Key。已经解决的载荷清除，只保留计数和必要的处理结果。条目数据限制沿用每分片最多 12 项、原响应最多 30000 字符，并另约束累计诊断载荷大小。

分片 phase 至少区分 extract_pending、extract_inflight、repair_pending、repair_inflight、done。分片完成不等于全部候选有效，质量结果由计数决定。正常等待下一请求也有显式检查点，不消耗网络重试额度。恢复时按 contract_revision 选择兼容解析器；遇到无法识别的版本则保留任务并提示升级，不能用另一版协议直接解释旧拒绝项。

新增事务入口负责「应用有效项＋保存逐项结果＋推进分片检查点」。已提交 sourceIndex 的动作不能再次执行。结果计数按稳定 sourceIndex 累计，不能把同一条每次重试都算成新的拒绝项。

详情接口改为显式选择公开的 job 字段，不再直接将 `SELECT *` 作为响应返回，以免新增检查点载荷使每次轮询膨胀。前端只需 lifecycle、outcome、计数和安全的原因摘要。

### 6.2 生命周期与质量分开

保留现有 pending/running/complete/failed 的 SQLite CHECK 约束，用 outcome 补充结果，避免重建任务表：

| 最终结果 | job.state / outcome | 展示 |
| --- | --- | --- |
| 合法初次空结果，且没有遗留错误 | complete / empty | 已处理；不因零卡片警告 |
| 所有输出已有效处理，含观察、排除、重复 | complete / ok | 已处理；卡片数不等于有效决策数 |
| 至少一项有效处理，仍有拒绝项或未完成分片 | complete / partial | 部分知识未能整理，已成功内容保留；提供继续处理 |
| 没有任何有效决策，仍有拒绝项或失败分片 | failed / invalid | 知识整理失败；提供继续处理 |
| 迁移前已完成且没有结果记录 | complete / legacy | 保留历史显示；不宣称新增质量校验通过 |
| 迁移前 v2 未完成且没有可靠检查点 | failed / legacy | 历史任务需重新核对；列出受影响范围，不作为普通自动重试 |

partial 必须同时提供 visibleChangeCount；只有 observe/exclude 通过时，文案不能说「已保留若干张卡片」。初始有拒绝项，纠正返回空数组时必须仍是 partial/invalid，绝不能转成 empty。

在所有分片终结或没有可自动执行工作时才聚合最终 outcome。某分片初次请求耗尽预算，也不应丢掉已成功分片；后续尚未处理分片仍有各自的一次基础请求机会，已经消耗的共享额外预算不恢复。401/403 或明确的全请求参数配置错误则终止本 job 的后续自动请求，把尚未执行分片保留给人工继续，避免用剩余分片重复验证同一个无效配置。

### 6.3 迁移与人工继续

v1/v2/v3 数据库逐级升级到 v4；收听 knowledge_policy_version 不变。已完成旧任务标为 legacy，不自动重算。只有 v4 新建的 v2 任务才自动初始化可靠检查点。迁移前没有检查点的未终结/失败 v2 任务统一标记 `legacy + LEGACY_RECOVERY_REQUIRED`，从自动队列隔离，提示「历史任务需重新核对」；不得凭 pending/attempts=0 判断它从未执行，因为旧人工 retry 会重置 attempts。

升级操作优先停止采集并排空旧任务。无法排空的 v2 旧任务进入显式历史恢复路径，普通继续处理不能假装恢复其不存在的逐项检查点；本轮保留原文和已有卡片，列出受影响任务，不自动重跑它们。v1 任务保留原行为与原有幂等保证，不承诺获得新的 v2 分片恢复能力。

现有 `/api/listenings/:id/retry` 扩展为处理 failed 及 partial 的未解决工作：在事务中开启新周期，只重置未完成分片的初次请求预算或未解决 ID 的纠正额度；已成功分片和已提交动作不重做。重复点击对 pending/running 幂等，不能无限重置在途预算。翻译失败重试规则保留。

当前用户那三条旧 complete 任务没有保存原模型响应及拒绝项，升级不能自动补回 Anthropic/Akamai，现有继续处理按钮也不会覆盖它们。旧完成记录的重新整理属于独立的显式恢复操作，需要重新读取原文和现有卡片，不能伪装成精准重试原拒绝项。本轮不静默重算或删除历史卡片；先验证新处理链路，再单独处理这条旧记录的恢复。

## 7. 用户状态与诊断

`processing().knowledge` 增加 partialJobs、unresolvedItems、repairPendingJobs、repairingJobs；重试等待和执行数量避免重复相加。修复过程中仍算 pending，结束后的 partial/invalid 不算自动 pending。

另提供 legacyRecoveryJobs 汇总迁移隔离任务，单独提示历史恢复限制；普通继续处理不将这类任务重新排队，也不因为它们单独显示一个实际无效的重试按钮。

- 纠正期间：「知识整理中，正在补全部分条目」。
- 部分未解决：「部分知识未能整理」，保留「继续处理」入口。
- 全部未解决：「知识整理失败」，保留已有其他批次内容。
- 缺少内存 Key：显示需要 API Key 继续；不空转轮询。
- 终态停止轮询，即使仍有部分问题也不无限自动请求；用户继续处理后恢复轮询。

详情响应、`processing-updated` 和前端 processingView 使用同一份聚合语义；不能出现数据库 partial、页面却只显示「已处理」。正常抽取无拒绝、无知识可收录的场景保持简洁。

保留现有 knowledge_job 时序字段；增加 returned_count、accepted_initial_count、resolved_count、normalized_count、rejected_initial_count、repaired_count、repair_excluded_count、unresolved_count、created_count、updated_count、observed_count、deferred_identity_count、visible_change_count、request_count、repair_ms、outcome、contract_revision。

拒绝日志输出 job/part/sourceIndex、错误码、字段路径及长度等必要信息，示例：`LABEL_INVALID @ display_label`、`QUOTE_TOO_LONG @ evidence[0].quote {length:561,max:300}`。不输出 Key、整段原文或原模型完整响应。不要再只打印「字段」。

增加首次有效内容提交时间以及相对 final 的耗时，用于区分「首批已显示、纠正仍在进行」；后台提交耗时不能冒充浏览器实际收到事件的耗时。卡片推送端到端延迟由集成测试或真实页面记录测量。

## 8. 主体筛选与候选上下文

生产提示词增加场景规则：新闻优先收录正在讨论的公司、产品、项目、研究或事件；仅充当报道署名、信息来源、节目串场的记者、主持人和媒体，通常不独立收录。当其本人、机构行为或作品成为主体、关键参与者或实质对比对象时，正常判断收录。

不建立「记者一律排除」职业黑名单，不硬编码 Anthropic、Akamai 或 Seth。来源身份容易判断，不应让模型优先输出来源而漏掉有明确依据的主体。明确核心对象第一次出现即可创建，不要求重复提及或等到收听结束。

为稳定后续更新，v2 `existing_candidates` 增加当前 short_description 和最多最近 2 条已存储事实，保留现有 ID、类型、名称、别名及对象数上限。每个候选的说明与事实合计不超过 600 字符，所有候选的说明/事实/旧摘要累计不超过 3600 字符；优先分配给与当前原文相关的候选。优先保留当前说明，再保留完整短事实；放不下的事实省略，避免截断到否定词或条件中间。旧 dialogue_summary 可兼容保留，但不再作为唯一状态，因为现实现更新后它仍可能是初始摘要。只使用已存储事实，不额外调用摘要模型。

此改动用于减少重复事实和错误 update/repeat，不保证实体召回率；主体质量必须用真实模型样本另行测量。

### 9.2 用户新闻样本：真实模型评估

将用户提供的三段原文作为固定样本，保留逐字文本；按整段一次输入、三段顺序输入、模拟最终句拆分三种方式回放。模拟最终句拆分必须标明是假设边界，不能当作用户原始 ASR 时序。

| 对象/信息 | 预期 |
| --- | --- |
| Anthropic | 必须有独立组织条目，第一段包含足够主体与交易依据后即可收录 |
| Akamai | 必须有独立组织条目，与 Anthropic 分开 |
| Claude | 可选；符合独立讨论价值时收录，不作为凑数指标 |

| OpenAI、Google、SpaceX、Netflix 等 | 此文本中多为对比或例子，不要求批量建卡 |
| 交易数额与期限 | 依原文记录 11.6 billion 美元，即 116 亿美元，期限七年 |

后续段落应对已有主体追加有依据的新事实，保持相同对象 ID；重复输入不因重新措辞重复建对象。含记者本人事迹的反例必须允许人物收录，避免只优化这一段样本。

真实调用需要可用的用户 API Key 和明确的评估调用范围；本轮方案阶段不使用真实 Key、不发生模型调用。没有真实评估结果时，交付只能写「行为回归通过，模型质量待测」，不得用手工 JSON 保证主体召回率。
