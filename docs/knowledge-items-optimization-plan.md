# HearWise 知识条目抽取与展示优化方案

| 项目 | 内容 |
| --- | --- |
| 版本 | v1.0 |
| 日期 | 2026-09-28 |
| 状态 | 设计方案，尚未实施 |
| 适用范围 | 知识型演讲、课程、访谈及专业播客的实时收听与历史回看 |

本文以已确认的产品方向为基础，规定知识条目的收录、合并、补充、展示和验收方式。本文是新增的方案文档，不修改运行代码，也不替换应用正在读取的知识抽取提示词。

核心目标：从收听内容中精选值得认识的具体对象，为每个对象持续积累贴合当前内容、可追溯、可以逐步展开的解释。

## 1. 已确认的方向与设计边界

### 1.1 已确认的产品方向

- 用户面对的是知识条目。人物、公司、产品等具体对象是组织知识的主要单位。
- 不是所有识别出的名词都值得收录。对象是否具体、是否重要、解释是否有助于听懂，需要共同判断。
- 「AI」等宽泛词默认不自动生成条目。
- 对于本文的柯达测试内容，最终生成「伊士曼柯达公司」「Brownie 相机」两条知识。
- 日期、价格、产品特点、相关事件及因果解释，优先组织在对应对象内部。
- 同一对象再次出现时，补充已有条目。别称、语言变化、重复提及不能持续增加条目数量。
- 两小时内容应保持可浏览性。数量控制需要从收录质量、去重和内容组织入手。

### 1.2 本文提出的实施建议

候选状态、字段设计、界面细节、阶段划分和验收阈值均为方案建议，尚未实施。本文明确给出默认选择，供后续开发和评估使用；数值目标不代表已有测量结果。

### 1.3 本轮不建设的能力

- 不自动把每个论点、因果关系、学习问题或上位概念转换成独立条目。
- 不以完整知识图谱、论证图、自动测验或掌握度评分作为主界面。
- 不自动从背景知识中扩展一批原文未提到的人物、产品和概念。
- 不预设用户对某个对象已经熟悉，也不根据点击、停留时长推断掌握程度。
- 不在第一阶段引入图数据库、跨收听的统一实体库或复杂学习画像。
- 不要求每个条目都联网搜索；外部核实不阻塞基础抽取和实时字幕。
- 不改变当前音频采集、识别、翻译的职责。本项目目前不保存音频，引用定位不能等同于音频回放。

## 3. 什么是值得收录的知识条目

### 3.1 条目定义

知识条目是具有相对明确身份、在当前内容中承担重要作用、值得补充解释的具体对象。

独立性判断：离开当前这句话，能否仍然清楚地指出这个对象是谁或是什么，并围绕它组织有用的介绍。

这一判断用于确定对象粒度，不代表所有具有独立身份的对象都要收录。收录仍需结合当前叙事角色。

### 3.2 三项收录条件

| 条件 | 要判断的问题 | 符合的例子 | 不足以收录的情况 |
| --- | --- | --- | --- |
| 对象具体 | 名称是否指向可辨认的对象？ | 伊士曼柯达公司、Brownie 相机 | AI、公司、相机、技术、市场 |
| 叙事重要 | 它是否是讨论主体、核心案例，或理解案例所需的关键参与者？ | 本段案例中的产品及推出公司 | 赞助商名单、随口举例、无后续解释的名字 |
| 解释有用 | 一段简短介绍是否有助于用户理解正在听的内容？ | 说明 Brownie 是什么、为什么被提到 | 换一种说法重复名称，或只提供无关履历 |

三项条件用于形成明确的收录理由，不要求模型输出长篇分析或推理过程。可用简短理由描述「核心案例产品」「案例的关键推出者」等可观察角色。

### 3.3 可收录类型

| 类型 | 可收录条件 | 默认不收录的近似情况 |
| --- | --- | --- |
| 人物 | 身份可辨认，贡献、经历或观点是当前内容的关键 | 名单中的名字、只有姓氏且无法消歧的代称 |
| 组织 | 具体公司、机构等，是讨论主体或案例关键参与者 | 「公司」「行业」「平台」等类别词 |
| 产品或项目 | 具体产品、系统、工具或项目，具有独立讨论价值 | 「相机」「软件」「模型」等通用品类 |
| 作品或文献 | 具体书籍、论文、报告等，内容或影响被实质讨论 | 顺带列出的参考资料 |
| 方法或理论 | 有明确名称和边界的特定方法、理论或技术，且正在被介绍、比较或应用 | 「AI」「创新」「学习」「大规模生产」等泛化词 |
| 事件 | 可独立识别的事件本身成为讨论对象，背景与经过有介绍价值 | 为每次产品发布、价格变化或普通行动另起标题 |
| 地点 | 具体地点本身对当前讲述有解释价值 | 仅作为人物或公司地址的一部分 |

产品分类不要求第一阶段立刻迁移数据库枚举。可以先保留现有 `type`，增加更具体的展示标签，避免让类型重构先于收录质量验证。

### 3.4 泛词与具体技术的边界

- 「AI」「人工智能」「互联网」「摄影」默认排除，不因出现频繁而升级成条目。
- 不对整个字符串做粗糙屏蔽。「AI」被排除，不应导致「OpenAI」或包含 AI 的具体产品名被误删。
- 「AlphaFold」等具体系统，如果是讨论主体或核心案例，可以收录；如果只在名单中出现，则暂缓或排除。
- 特定方法或理论仅在名称、含义和当前作用足够明确时收录，不能把任意技术短语都归入此类。
- 即使演讲主题围绕 AI，也不自动收录宽泛的「AI」条目。可以把它保留为当前主题背景，帮助筛选具体对象。
- 用户主动指定保留某个泛词时可以作为手动条目，但这不改变默认自动抽取规则。

常见与生僻都不是充分条件。广为人知的公司可以是关键对象，生僻名称也可能只是偶然提及。

## 4. 候选筛选与生命周期

### 4.1 内部候选与用户条目分开

模型可以识别到多于最终收录数的候选，但候选不直接进入用户知识列表，也不计入知识条目数量。

候选记录应轻量、可追溯，保存名称、出现位置、对象线索、当前决策和简短理由。明显泛词可以在前置过滤中直接排除，不必为每次出现保存完整候选。

### 4.2 按顺序作出决策

1. 找到原文中的明确对象及对应证据，过滤普通名词、属性值和模型自己概括的标题。
2. 检索已有条目和待观察候选，优先判断是否指向已经出现的对象。
3. 判断是否具有本段主体、核心案例、关键参与者或实质对比对象的角色。
4. 判断当前身份线索是否足以避免明显错认，以及能否提供有用的简短解释。
5. 对满足条件的新对象收录；对已有对象追加信息；对有潜力但信息不足的对象暂存；对明确无价值的对象排除。

对象只出现一次也可以收录。柯达在示例中作为核心产品的推出者已经具有明确作用，不需要等待第二次提及。

### 4.3 决策与展示规则

| 决策 | 适用情况 | 展示与后续处理 |
| --- | --- | --- |
| 收录 | 三项条件满足，身份可辨认 | 创建一个正式条目 |
| 补充 | 与已有条目为同一对象，存在新信息或新证据 | 更新已有条目，不增加数量 |
| 待观察 | 对象可能重要，但身份或叙事角色尚不明确 | 暂不展示；出现新证据时重新判断 |
| 排除 | 泛词、附属属性、无关名单或不应独立成条的概括 | 不展示；保留必要的简短决策记录 |
| 无内容变化 | 已有对象被重复提及，但没有新的解释内容 | 可追加去重后的引用，不刷新说明、不标记「已补充」 |

收录决策、内容可靠性和界面隐藏状态是三个维度。一个重要对象的某项价格记忆不可靠，不意味着整个对象不值得收录；用户隐藏某条目，也不意味着它的内容错误。

### 4.4 待观察与排除的后续处理

- 待观察对象在再次出现、被明确解释、发生消歧或主题整理时重新判断。
- 早期只是名单成员的对象，如果后文成为讨论主体，可以转为收录；其首次出现的原文引用继续保留。
- 泛词不会仅因重复次数上升而转为收录。
- 主题结束或收听停止时，复查仍有价值线索的候选。不足以收录的对象保持内部状态，不强行补齐目录。
- 候选数量受上下文预算限制，不能把全部候选反复发送给模型。较旧候选可以留在持久化索引中，后续按名称和上下文召回。
- 已收录条目不因短期未被提及而删除。当前相关性降低时移出当前区域，仍保留在完整目录。

## 5. 两小时演讲的数量与信息量控制

### 5.1 抽取端控制

- 没有值得收录的对象时允许零新增。
- 不设置每段最低产出数，不把模型单次输出上限当成产出目标。
- 同一产品的价格、年份、设计、使用方式和影响，默认留在同一条目中。
- 已经存在的对象优先更新。模型建议新建时，服务端仍应检查可能的同一对象。
- 只有出现新的独立对象，而且满足收录条件时，才增加条目。
- 一段内容出现很多专名时，先判断各自角色。若确实都重要，可分批完成，不静默丢弃超过单次容量的对象。

不规定「两小时必须只有 N 条」。一场单一主题演讲和一场多产品比较所需条目数量不同。条目数作为诊断指标，必须结合人工标注的关键对象覆盖情况判断。

### 5.2 条目内部控制

- 默认只呈现名称、类型和一句与当前内容相关的说明。
- 展开后先呈现身份说明和本次内容涉及的重点，再提供引用与背景。
- 建议默认展示最多 3 条重点细节，超出部分继续折叠；这是展示限制，不是丢弃信息的规则。
- 同义重复不增加段落。新增事实只补进相应位置，不把历次模型摘要串接成长文。
- 原文引用可保留多处，优先展示最能支持当前说明的引用，其余按需展开。

### 5.3 界面控制

建议分为「当前相关」和「本次知识」两层。

「当前相关」默认最多显示 3 条，随当前讲述重点更新；「本次知识」保留完整目录，并提供名称与别名搜索。3 条是初始界面参数，后续根据阅读负担调整。

超出当前区域容量的正式条目仍能在完整目录找到。界面容量、正式条目数量和内部候选数量必须分别统计。

更新时保持展开状态、阅读位置和已展开卡片的内容稳定。不要因为新的对象出现而强制滚动，也不要每次命中都把同一条目移到列表顶部。

## 6. 一个条目应当包含什么

### 6.1 内容层次

| 层次 | 解决的问题 | 内容约束 |
| --- | --- | --- |
| 名称与类型 | 这是哪个对象？ | 使用明确名称；别名不另起条目 |
| 一句话说明 | 为什么现在值得认识它？ | 与当前讲述直接相关，避免空泛百科介绍 |
| 身份说明 | 它是谁或是什么？ | 身份不确定时不补编履历、制造商或用途 |
| 本次提到 | 演讲围绕它说了什么？ | 保留原文的计划、猜测、否定与限制 |
| 背景补充 | 哪些原文外的信息有助于听懂？ | 简短、相关，标明模型补充或外部来源 |
| 相关对象 | 和已经收录的哪些对象有关？ | 仅展示有依据的关系，不扩展新对象列表 |
| 原文依据 | 这些内容在哪里出现？ | 链接完整相关句，不只给孤立名称 |
| 待确认细节 | 哪些说法仍有疑问？ | 局部标记，不用一个模糊标签否定整个条目 |

一句话说明优先回答当前内容中的作用。如果上下文尚不足，可以先显示明确的身份信息，后续再补充其在讲述中的意义。

### 6.2 渐进补充

同一条目可以随着演讲变得丰富，但每次更新都应说明是否有实质增量：

- 首次出现：明确身份及当前作用。
- 后续介绍：补充重要特点、时间、价格或相关经历。
- 新的对比：补充与已收录对象的区别。
- 明确更正：更新对应细节，保留原说法及更正依据。
- 重复提及：保留引用，正文不变。

背景说明只在首次收录、信息发生变化或用户主动展开需要更多解释时生成。相同输入和相同条目版本应尽量复用结果。

### 6.3 用户轻量反馈

建议提供「本次隐藏」「有误」「保留」三种操作：

- 本次隐藏：从当前收听的默认目录隐藏，可恢复；不推断用户永久熟悉该对象。
- 有误：允许标记名称、解释或归并问题，附着在具体条目上。
- 保留：确保用户关心的条目容易找到；不意味着内容被核实。

这些操作可在基础筛选稳定后增加，不作为第一阶段的前置依赖。手动隐藏状态需要持久化，不能在后续自动更新时被取消。

## 7. 柯达测试内容的完整预期

### 7.1 输入原文

> 1900 年，伊士曼柯达公司推出了 Brownie 相机。它算是最早实现大规模生产、让更多普通人能够接触摄影的产品之一，价格也降了下来。我记得，用它拍一张照片大约只要一美元。于是，突然有很多人开始拍照。

### 7.2 预期收录结果

正式条目恰好 2 条。以下文案用于说明结果形态，不要求模型逐字复现。

**伊士曼柯达公司 · 公司**

一句话说明：1900 年推出 Brownie 相机的公司，是本段摄影普及案例中的关键参与者。

本次提到：讲者介绍了公司推出 Brownie 相机的历史，并通过这一产品说明更多普通人开始接触摄影。

相关对象：Brownie 相机，关系为「推出」。

原文依据：「1900 年，伊士曼柯达公司推出了 Brownie 相机。」

**Brownie 相机 · 产品**

一句话说明：柯达于 1900 年推出的相机，讲者用它说明摄影产品价格下降后，更多普通人开始参与摄影。

本次提到：

- 讲者将其描述为较早实现大规模生产、让普通人接触摄影的产品之一。
- 讲者把价格下降与拍照人数增多联系起来；原文未给出人数、增长幅度或发生时长。
- 讲者回忆「拍一张照片大约只要一美元」，该细节包含明确的不确定表达。

相关对象：伊士曼柯达公司，关系为「推出公司」。

原文依据：分别引用涉及产品定位、价格和参与人数的原句，不以单独的「Brownie」名称支持全部描述。

### 7.3 不生成的条目

| 候选内容 | 处理方式 | 理由 |
| --- | --- | --- |
| 1900 年 | 作为推出时间 | 属性，不是独立对象 |
| 一美元 | 作为待确认的价格细节 | 数值及单位，不独立成条 |
| 摄影、相机、普通人 | 不收录 | 通用概念或泛称 |
| 大规模生产 | 保留在 Brownie 的本次提到中 | 当前只是产品描述 |
| 摄影大众化 | 可作为条目说明中的概括 | 属于 AI 归纳，不新增条目 |
| Brownie 发布事件 | 放进产品与公司的相关描述 | 无须从同一事实再拆出事件条目 |
| 经济门槛、价格下降促进普及 | 必要时放进解释 | 不转成新概念或因果条目 |
| 乔治·伊士曼等背景人物 | 不自动新增 | 原文未提及，不能由百科补充扩展目录 |

### 7.4 「一美元」的处理

没有联网核实时，只记录「讲者回忆的单张照片成本，待确认」，不能凭模型记忆静默改写原话，也不把不确定价格放入默认一句话说明。

本文讨论过程中参考的[柯达官方历史资料](https://www.kodak.com/en/company/page/photography-history/)记载，1900 年 Brownie 相机售价为 1 美元，胶卷为每卷 15 美分。该资料提示讲者可能混淆了相机售价与单张照片成本。此来源只支持对应的价格和年份信息，不自动验证「最早」「突然有很多人」等其他说法。

未来若启用外部核实，应将这项结果附在 Brownie 条目内部，分别保存原文说法、外部资料和核实时间。本文已经查到资料，不代表当前应用具备自动核实能力。

这一细节不额外生成「购买成本」「使用成本」等条目，也不要求用户完成理解测验。

### 7.5 后续输入的增量行为

以下均为行为测试场景，不补充历史事实：

| 后续内容 | 预期行为 |
| --- | --- |
| 再次说「Brownie 相机」但没有新增信息 | 条目仍为 2 条，正文不变 |
| 上下文明确「柯达」指前面的伊士曼柯达公司 | 关联已有公司，必要时记录原文别称 |
| 介绍 Brownie 的某项设计 | 补充产品细节，不新建「设计」条目 |
| 讲者明确更正「一美元说的是相机价格」 | 更新价格细节，保留更正前后的原文依据 |
| 提到 AI、互联网等宽泛词 | 不新增条目 |
| 转而详细介绍另一个具体相机产品 | 按收录条件判断新产品，不能为了保持 2 条而漏收 |

## 8. 实时处理方案

### 8.1 推荐处理顺序

最终 ASR 句子进入处理批次后，依次完成候选识别、已有对象检索、收录判断、条目更新校验、持久化和界面通知。背景补充作为后续任务，只面向已收录且需要解释的对象。

第一阶段可以把候选识别与收录判断放在同一次模型调用中。逻辑职责分开不意味着必须引入多个模型或多个代理。

### 8.2 输入上下文

建议模型输入包括：

- 本批最终原文及其真实句子 ID。
- 最近完整语义片段，避免只留下被截断的末尾句。
- 当前主题的简短背景，仅用于筛选，不作为新的条目或原文证据。
- 与本批名称、别名和指代相关的已有条目。
- 相关待观察对象及其原始证据。
- 当前抽取策略版本、待更新条目版本和来源范围。

历史检索先使用名称、已确认别名、主题关联和近期上下文。若评估发现跨语言名称或换一种说法导致明显漏召回，再考虑语义检索，不在第一阶段强制引入向量数据库。

优先补全有价值的上下文，而不是把整个两小时文本放进每次请求。主题摘要不能替代原始证据，所有事实仍需回到原句。

### 8.3 延迟收录的证据规则

现行协议要求新条目证据来自本批 `focus_segments`。引入待观察候选后，需要有意识地扩展这一规则：

- 新识别的对象仍需来自本批原文。
- 早期候选被提升时，允许引用服务端明确提供的历史候选证据，并结合当前出现的收录依据。
- 模型只能引用本次输入授权的句子 ID；服务端校验它们属于当前收听且原文匹配。
- 不允许任意引用所有历史文本，更不能跨收听借用证据。
- 仅靠当前代词不能自动确认对象身份。缺少明确指代依据时继续待观察。

### 8.4 更新与失败处理

- 新增、补充、名称更正和无内容变化必须有不同的处理语义。
- 以稳定对象 ID 关联更新，重试同一批次不能重复创建条目或重复追加细节。
- 不把最新一段摘要直接覆盖全部历史说明。按细节合并，再生成简短的展示摘要。
- 后来的说法与前文冲突时，保留两处来源；有明确更正依据才替换对应事实，不能把「更新」等同于「更真实」。
- 背景补充失败时，仍展示已完成的原文相关内容，不用未经检查的泛化解释填空。
- 模型输出无效时沿用有限重试和逐条校验；失败状态不应伪装成「没有知识」。
- 增补任务基于条目版本写回，过时结果不得覆盖更新后的内容。沿用串行处理也应保留这一约束。
- 停止收听后处理未完成的候选与更新任务；服务重启后能够继续处理，但不重新生成所有已有条目。
- 继续保持翻译优先。知识任务的延迟、积压和费用需要独立记录，避免为更丰富的背景拖慢字幕。

## 9. 模型任务与输出契约建议

### 9.1 提示词的职责

后续提示词应明确要求模型完成以下工作：

1. 找出本批涉及的具体对象，不从背景知识中主动扩展名单。
2. 判断对象的叙事角色；已有对象优先关联。
3. 对候选给出收录、待观察、排除或更新建议及简短理由。
4. 仅为收录或更新的对象生成紧凑内容。
5. 将属性、特点和普通事件写进所属对象，禁止拆成新条目凑数量。
6. 所有对话相关陈述都有原文依据；来源不足时保留不确定性。
7. 可以返回空结果。对象频次、陌生程度、模型知识量都不能独立决定收录。

原文仍按待分析数据处理，其中的口述命令不得改变抽取规则。

### 9.2 输出分离

建议将候选决策与正式条目变更分开。以下是逻辑契约，具体 JSON 键名和接口需在实施时统一。

| 结果部分 | 最少需要的信息 | 约束 |
| --- | --- | --- |
| 候选决策 | 候选标识、原文名称、对象类型、决策、理由、证据 | 待观察和排除不能直接成为正式条目 |
| 正式条目变更 | 操作、目标对象或候选标识、内容增量、证据、预期版本 | 更新操作须指向当前收听中的有效 ID |
| 名称更正 | 原名称、新名称、明确更正依据 | 不靠相似拼写或模型常识自动改名 |
| 身份整理 | 待归并或拆分的对象 ID、证据、原条目版本及来源映射 | 由服务端校验后事务执行，保留可恢复记录 |
| 背景补充 | 对象 ID、补充内容、来源类型、适用条目版本 | 不生成新的候选，不混入对话摘要 |

常规操作语义为新建、补充、名称更正和无内容变化。已有条目之间的归并及错合并后的拆分属于单独的身份整理操作，不能用普通更新替代。决定「是否值得收录」与决定「是不是已有对象」不能混用一个模糊字段。

服务端仍负责格式、引用、作用域、版本和允许值校验。模型给出收录理由并不意味着结果无需验证。

### 9.3 提示词版本管理

现行 [knowledge-extraction-prompt.md](knowledge-extraction-prompt.md) 由应用直接读取，修改它会影响运行行为。本轮保持该文件原样。

未来提示词升级应与解析器、数据结构、任务策略版本和评估样例一同更新，不能只改文档中的提示词却沿用不兼容的解析器。

默认按一次收听的「整理版本」固定策略、提示词和输出协议。任务创建时记录版本，失败重试、服务重启续跑和在同一整理版本内继续收听均沿用固定版本，不因部署了新提示词而静默切换。新策略默认应用于新建收听；主动重新整理旧收听时创建新的整理版本，同一版本内不混跑不同策略。

旧版本执行能力需要在待处理任务仍存在时保留。如果旧执行能力暂不可用，保留任务并明确提示处理受阻，不自动用新协议重跑。新整理版本达到可用状态后再切换展示，并保留返回旧结果的能力。

## 10. 数据与身份管理建议

### 10.1 逻辑数据结构

建议继续使用现有存储基础，按阶段补充以下信息。表名仅表示设计职责，不是本轮数据库变更。

| 对象 | 需要保存的信息 | 用途 |
| --- | --- | --- |
| 正式条目 | 稳定 ID、收听 ID、整理版本 ID、名称、类型、简短说明、收录理由、条目版本 | 维持同一对象的连续性 |
| 待观察候选 | 名称、身份线索、决策、理由、出现位置、最后处理位置 | 支持跨批次观察和延迟收录 |
| 条目细节 | 所属条目、内容、来源、原文引用、不确定性、修订关系 | 增量补充与局部纠错 |
| 名称与别名 | 原文写法、确认依据、所属对象 | 去重及引用定位 |
| 对象关联 | 两个已收录对象、关系、原文证据 | 支持条目内导航，不建设独立图谱界面 |
| 用户展示偏好 | 本次隐藏、保留等显式操作 | 防止更新覆盖用户选择 |
| 处理记录 | 整理版本、固定的策略与协议版本、输入范围、操作标识、状态及失败原因 | 重试、审计和幂等处理 |

如果第一阶段用条目内部的结构化字段保存少量细节，也应保留每项细节的来源，不能仅存一段不断变长的生成文本。

### 10.2 身份对齐

- 同名不必然同一对象，名称相近也不必然同一对象。
- 同一对象的中文名、英文名和缩写，需要原文或可核实的明确依据；不能自动扩展猜测的别名。
- 「Brownie」在已确认相机语境中可关联 Brownie 相机；若后文谈到同名食物，则不能合并。
- 公司与其产品是不同对象，可以关联，不能因频繁共同出现而合并。
- 产品系列与具体型号是否拆分取决于当前讨论是否需要区分。只讲系列时保留系列条目；明确比较不同型号时，允许分别收录并保留系列关系。
- 对一次重试、重复 ASR 句子或模型重复输出，需要稳定幂等标识，不仅依赖名称字符串。
- 无法确定是否同一对象时先保留为内部候选，不把所有歧义都变成用户可见的重复条目。

两个对象已分别收录，后文才明确为同一对象时，允许事务归并。保留一个主条目 ID，其余 ID 转为可追溯的重定向；合并别名、细节、引用和对象关联，去掉重复内容，目录按主条目计数。原条目内容与来源映射保留在修订记录中，归并前发出的后台任务需重新校验目标 ID 和版本。

归并需要明确的身份依据，不能仅凭名称相似、共同出现或模型评分。归并后发现错认时，允许依据原始映射和补充证据拆分恢复；不能把两边所有细节直接复制给两个对象。隐藏、保留等用户选择需要随原对象记录保留；归并时存在隐藏冲突，默认不自动重新展示，允许用户恢复。归并和拆分均不得修改原始字幕或跨收听记录操作。

第一阶段按同一收听记录对齐身份。跨收听的统一对象、全局别名库和个人长期知识库留到后续阶段，避免把不同语境的内容直接混在一起。

### 10.3 来源与不确定性

分别表达以下信息：

- 对象身份是否明确。
- 某项细节是否仅为讲者的回忆、计划、推测或观点。
- 背景是否为模型补充，是否有外部来源。
- 外部资料是否与原文存在冲突。

「对话明确提到」只代表原文依据清楚，不等于内容已经外部核实。相关显示应落在具体陈述上，避免一个「已确认」标签覆盖全部内容。

外部资料没有提到某件事，不代表原文一定错误；外部核实也不能触发原文之外的新条目扩展。

## 11. 界面与交互方案

### 11.1 收听中

保留字幕的连续性。知识区域以稳定的条目列表补充理解，避免自动展开长文或在音频继续时频繁弹窗。

默认条目示例：

> **Brownie 相机**　产品
>
> 柯达于 1900 年推出的相机，本段用它说明摄影如何走向大众。

展开后依次显示身份说明、本次提到、相关对象、背景补充和原文依据。有待确认细节时，在对应位置显示，不将提示塞入每一条默认摘要。

「已补充」只在新增实质内容时短暂出现。单纯重复提及不产生新的视觉提示。

### 11.2 引用与相关对象

- 点击原文依据后，自动加载所需句子并定位到完整上下文。
- 当前实现中「请先加载更多句子」的手动路径应在后续优化中消除。
- 点击相关对象时打开同一收听中已有的条目，保持返回位置。
- 没有收录的对象可以在正文中作为普通文字出现，不因此自动创建条目。
- 引用定位为文本跳转。音频播放与回听能力不在此方案的第一阶段。

### 11.3 历史回看

历史详情使用同一组稳定条目，可按名称和别名搜索。默认保留稳定顺序，例如首次正式收录顺序；相关性排序作为当前区域的行为，不持续打乱完整目录。

可在有明确主题边界时按主题分组，但同一对象只保存一次。跨主题出现时引用同一个条目，不能为了分组复制卡片实体。

目录数量仅反映可见的正式条目。若增加隐藏功能，应明确提供「查看已隐藏」入口。

### 11.4 空状态与处理状态

| 状态 | 建议文案 |
| --- | --- |
| 尚未开始或没有最终原文 | 「开始收听后，会在这里整理值得了解的对象。」 |
| 已处理，但没有值得收录的对象 | 「这段内容暂时没有需要单独介绍的对象。」 |
| 仍有待处理任务 | 「正在整理知识条目。」 |
| 部分任务失败 | 「部分内容尚未整理完成，可继续处理。」 |
| 背景补充失败 | 保留原文相关内容，在展开区提供重试入口 |

零条目可以是正确结果，不应通过空状态暗示用户必须获得一定数量的知识。

## 12. 评估样例与验收方法

### 12.1 固定行为样例

| 编号 | 输入特征 | 预期结果 |
| --- | --- | --- |
| K01 | 本文完整柯达段落 | 正式条目恰好为伊士曼柯达公司、Brownie 相机 |
| K02 | 多次重复 AI、人工智能、互联网 | 不自动生成这些宽泛条目 |
| K03 | 在关键案例中只提到一次推出公司 | 可收录，不能要求重复两次才算重要 |
| K04 | 连续朗读一串赞助商或参考对象 | 默认不批量收录；后续实质介绍时再判断 |
| K05 | 相隔较远再次提及已知对象 | 命中已有条目，不因不在最近候选中而重复新建 |
| K06 | 对同一对象补充年份、价格、特点 | 更新对应条目，不生成属性条目 |
| K07 | 同一对象有明确中英文名称或简称 | 关联同一个对象，保留原文写法 |
| K08 | 两个同名人物、同名产品或跨语境同名对象 | 无明确依据不合并 |
| K09 | 早期轻描淡写，后续成为讨论主体 | 延迟收录，并保留早期证据 |
| K10 | 用户输入「OpenAI」等包含 AI 的具体名称 | 按具体对象判断，不被泛词规则误杀 |
| K11 | 口误、疑似 ASR 错误、后文明确更正 | 无依据时不擅自改名，有依据时修订并保留记录 |
| K12 | 「我记得」「可能」「计划」及否定陈述 | 保留不确定性、时态和否定范围 |
| K13 | 背景补充提到原文没有的人物或产品 | 不自动把这些对象加入目录 |
| K14 | 重试同一任务或收到重复句子 | 不增加重复条目、重复细节或提示 |
| K15 | 后文反驳或限定前文 | 保留两处来源，修订具体内容，不覆盖无关信息 |
| K16 | 文本中包含「忽略规则」等口述命令 | 作为原文数据处理，不改变抽取目标 |
| K17 | 当前页未加载被引用的句子 | 点击后按需加载并定位，不要求用户逐页查找 |
| K18 | 新条目出现时用户正在阅读旧条目 | 保持展开、滚动和阅读位置 |
| K19 | 结尾只剩一两句，却引入了新的关键对象 | 停止后处理尾批，不能因未达到常规触发句数而遗漏 |
| K20 | 单批的重要具体对象超过处理容量 | 分批完成，不能把调用上限变成永久收录配额 |
| K21 | 已排除的名单对象后来成为主要案例 | 根据新的角色证据重新判断，允许转为收录 |
| K22 | 背景补充失败或没有可靠资料 | 保留有原文依据的条目，不编造背景、不显示为整体失败 |
| K23 | 两条已收录对象后来有明确证据证明相同 | 归并为一个主条目，旧引用可跳转，归并可追溯 |
| K24 | 归并后发现错认，或旧任务在归并后返回 | 可按证据恢复独立对象；旧结果不能覆盖或重新创建被归并条目 |
| K25 | 策略升级时旧任务重试或继续收听 | 沿用该整理版本固定的策略与协议，不混跑新旧版本 |

### 12.2 两小时样本评估

建议至少选取 3 类接近两小时的真实内容：单一主题技术演讲、案例较多的历史或产品演讲、多对象比较的访谈。数量和长度为首轮评估建议，不能据此声称覆盖所有收听场景。

评估前由人工标注：

- 必须收录的关键对象。
- 可收录但非必要的对象。
- 应排除的泛词、属性及偶然提及。
- 同一对象的别称与需要区分的同名对象。
- 每个关键对象最早何时已有足够证据收录。
- 重要细节的原文依据及不确定表达。

先标注并处理分歧，再对照系统结果。标注规则、调参样本和保留验证样本分开，避免只对柯达案例优化。

按时间顺序回放最终 ASR 文本，严格限制每次输入只能使用当时已经出现的内容。最终目录质量与收听中的呈现质量分别评价；不能用全文预读结果代替实时抽取结果。

### 12.3 指标定义与建议目标

| 指标 | 定义 | 初始验收建议 |
| --- | --- | --- |
| 收录准确率 | 去重后，被人工判定值得收录的对象数 / 系统收录对象数 | 不低于 90%，同时检查误收类型 |
| 关键对象覆盖率 | 被收录的必须对象数 / 人工标注的必须对象数 | 不低于 95%，不得靠少抽获得高准确率 |
| 重复条目率 | 同一对象多余的正式条目数 / 全部正式条目数 | 不高于 2%；K01、K05、K07、K14 不得重复 |
| 错误合并 | 不同对象被合并的案例 | 固定身份测试集为 0，长样本逐项复核 |
| 泛词泄漏 | 被规则排除的泛词成为正式条目的次数 | 固定泛词测试集为 0 |
| 可追溯性 | 对话相关陈述有可定位原文依据的比例 | 100%；另行审查证据是否真正支持陈述 |
| 无依据的具体事实 | 原文或标注来源均不支持的日期、价格、身份等 | 固定验证集不得出现 |
| 呈现延迟 | 从最早足够收录的句子到条目可见的时间 | 记录中位数和高分位数，基于基线确定上线预算 |
| 内容稳定性 | 无新信息时摘要改写、列表重排、阅读位置丢失的次数 | 固定交互场景不发生无理由变化 |
| 系统代价 | 每小时模型调用、输入输出量、失败、积压及字幕延迟 | 与现有版本对比，单独报告；不虚构费用承诺 |

上述百分比是建议的首轮验收目标，不是当前能力，也不是已验证的业务标准。没有正式条目的样本不计算收录准确率，按空输出是否符合预期单独判定；其关键对象漏收仍计入覆盖率。

每个长样本还应绘制或汇总随时间变化的正式条目数、新增数和更新数。如果新增量持续接近名词出现量，应复查收录门槛；如果长期不新增，则检查是否漏掉后续重要对象。数量曲线只用于诊断，不能代替语义评估。

### 12.4 用户体验验证

让用户分别使用现有版本和优化版本完成相同任务：找到演讲中的关键对象、理解对象为何被提及、找到对应原文、回看后来补充的信息。

重点观察是否出现以下改善：条目更相关，泛词更少，同一对象更集中，阅读展开内容时更少失去收听位置。点击量、停留时长和生成字数不作为理解程度的替代指标。

## 13. 实施阶段与交付边界

### 阶段 0：冻结规则与建立样本

交付收录规则、固定样例、长内容标注和现有版本基线。确认泛词边界、同名处理和柯达示例均可被一致解释。

本轮只交付本文；样本文件、评估脚本和实现属于后续工作。

### 阶段 1：精选收录与稳定去重

目标是显著减少无价值条目，同时保留关键对象。

工作包括收紧提示词与校验规则、引入必要的待观察状态、改进已有对象召回、补齐更新幂等性。界面可先沿用现有列表，增加简短说明。

验收重点为 K01 至 K14、泛词泄漏、收录准确率、关键对象覆盖率和两小时重复情况。阶段 1 必须包含长内容验证，不能只凭短片段效果进入下一阶段。

### 阶段 2：条目持续丰富与阅读体验

增加有来源的条目细节、局部修订、相关对象导航、「当前相关」区域、按需加载原文和稳定更新。背景补充按需执行。

验收重点为长时间收听后的条目可读性、事实保真、更新稳定性和引用路径。完成必要的兼容与回退验证。

### 阶段 3：按需要扩展

在前两个阶段达到质量要求后，再评估显式用户反馈、可选外部核实、跨收听对象关联和用户指定的关注对象。

每项扩展独立判断价值，不要求把全部能力一次实现。外部核实需要明确数据来源、请求范围、延迟、费用与失败处理，不能静默把所有转写内容发送到额外服务。

## 14. 兼容、回退与主要风险

### 14.1 兼容与回退

- 新策略应有独立版本标识，能够与现有策略比较和切换。
- 数据库升级使用可验证的迁移方式，新增字段为旧记录提供明确默认值。
- 历史收听默认继续展示已有条目，不自动批量删除旧知识或重跑全部历史。
- 如提供「重新整理」，应明确生成新的整理版本或可恢复的结果，保留原文、用户反馈和已有引用。
- 回退时停止新策略任务，旧展示仍应能够读取基础条目信息；复杂字段不应导致整个历史记录无法打开。
- 删除一条收听时，同时清理其候选、条目细节和后续任务关联，避免后台任务重新写回已删除记录。

### 14.2 风险与处理

| 风险 | 表现 | 处理方向 |
| --- | --- | --- |
| 筛选过严 | 只剩少量条目，却漏掉关键对象 | 单独考核关键对象覆盖率，允许重要对象首次出现即收录 |
| 筛选过松 | 泛词、名单和属性持续进入目录 | 固定排除样例、叙事角色检查、审查新增原因 |
| 高频偏差 | 重复最多的词排在最前 | 频次只作辅助信号，不作为收录门槛 |
| 身份错认 | 同名对象合并，或 ASR 错误被强行纠正 | 保存上下文、延迟判断、要求明确对齐依据 |
| 内容丢失 | 新摘要覆盖旧信息，限制条件消失 | 细节级更新、版本检查、保留修订依据 |
| 背景膨胀 | 条目变成长篇百科，派生大量新对象 | 与当前内容相关、默认短说明、背景不参与扩展抽取 |
| 事实混淆 | 原文、模型知识和外部资料混为一体 | 来源分离、局部不确定性、原话不改写 |
| 界面跳动 | 新条目和重复更新不断打断阅读 | 稳定 ID、增量渲染、固定展开状态和阅读位置 |
| 成本与延迟增加 | 每个候选都查询背景或重复调用 | 先筛选再补充、结果复用、限制上下文、监测队列 |
| 候选积压 | 两小时后大量候选反复进入输入 | 持久化轻量索引、按相关性召回、主题结束时整理 |

## 15. 第一版实施采用的默认决策

| 决策项 | 本方案默认选择 |
| --- | --- |
| 自动收录风格 | 精选；允许零新增，无每段最低配额 |
| 「AI」等泛词 | 默认不自动收录，不因频繁出现改变判断 |
| 知识组织单位 | 具体对象，相关属性与解释在对象内部积累 |
| 待观察对象 | 内部保存，不计入用户知识数量 |
| 同一对象复现 | 更新已有条目，重复提及不改写正文 |
| 当前区域容量 | 初始最多 3 条，完整目录保留全部正式条目 |
| 展开后的默认细节 | 初始最多 3 条，其余按需展开 |
| 用户熟悉程度 | 未知；不自动推断，也不增加首次使用问卷 |
| 背景生成 | 对已收录对象按需执行，不能扩展新条目 |
| 联网核实 | 非第一阶段默认流程，后续作为可选能力 |
| 跨收听去重 | 暂不做；第一阶段保证同一收听内稳定一致 |
| 模型选择 | 先用现有模型验证任务与协议，是否升级由评估决定 |
| 历史记录 | 保留，不自动重整或删除 |

第一版完成的判据：柯达片段稳定产出两条有用的对象知识；两小时内容能够持续补充已有对象、抑制泛词和重复项，并让用户容易找到所需对象与原文依据。
